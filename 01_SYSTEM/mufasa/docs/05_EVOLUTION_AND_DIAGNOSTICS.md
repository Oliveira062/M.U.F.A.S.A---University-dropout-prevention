# MUFASA — finding errors and evolving the system

This document is for whoever is going to maintain MUFASA. It covers how to find an error quickly when something fails and how to change the system without breaking what already works.

## 1. The tools, in short

| Tool | Command or place | What it is for |
|---|---|---|
| Support code | appears on the screen next to the error | Links what the user saw to the exact record of the error |
| Logs | `logs/` folder | History of everything each service did |
| Diagnostics | `python -m scripts.diagnostics` | Checks the whole system and points out what is wrong |
| Search by code | `python -m scripts.diagnostics --request <code>` | Finds the error from the code on the screen |
| Service health | `/health` and Administration → Services | Says whether each part is up and with which version |
| Technical logs | Administration → Logs (`technical_logs` table) | Errors saved in the database, visible in the dashboard |
| Migrations | `python -m scripts.migrate` | Changes the database in a controlled and recorded way |
| Automatic tests | `pytest` | Makes sure the change did not break anything (201 tests) |
| Version | `app/__init__.py` and `CHANGELOG.md` | Says what changed in each version |

## 2. When an error happens: the fastest path

1. **Write down the code that appears on the screen.** Every error shows "Code for support: …":
   - a code like `3f9a1c0b2d4e` came from the API or the chat;
   - a code like `P-1a2b3c4d` came from the dashboard itself.
2. **Search for the code:**
   ```bash
   python -m scripts.diagnostics --request 3f9a1c0b2d4e
   ```
   The command shows the log lines with that code (route, response, time and the error stack) and the record in the database, if there is one.
3. **If there is no code** (for example, "the system does not open"), run the full diagnostics:
   ```bash
   python -m scripts.diagnostics
   python -m scripts.diagnostics --output report.txt      # to send to whoever is going to fix it
   ```
   Each item comes out as `ok`, `WARN` or `FAIL`, with a tip on what to do. The report contains no password, token or student data, so it can be sent.
4. **Fix it, run `pytest` and check again** with the diagnostics.

## 3. The logs

Each service writes to the `logs/` folder (or to `MUFASA_LOG_DIR`):

| File | What it has |
|---|---|
| `api.log`, `chat.log`, `calculation.log`, `dashboard.log` | Structured logs of each service |
| `<service>.console.log` | Everything the service printed, including startup errors (only through `start`) |
| `logs/tests/` | Logs generated by the tests |

Format of a line:

```
2026-10-28 08:43:32,109 INFO    [api] mufasa.requests: req=98e431284b85 GET /api/v1/account/me -> 200 in 6 ms
   date and time        level   service  origin         code          route              response time
```

- **What is logged:** each request, with code, route, response and time. A request with error 500, or slower than 2 seconds, becomes `WARNING`. Errors come with the full stack.
- **What is never logged:** password, token and student data. The route appears as a template, for example `/students/{enrollment}`, never with the real student ID.
- **Size:** each file goes up to 5 MB and keeps the last 5 copies (`api.log.1` to `api.log.5`), so the folder does not grow without limit.
- **More detail:** `MUFASA_LOG_LEVEL=DEBUG` in `.env` and restart. Go back to `INFO` afterwards.

## 4. Failure isolation: what happens when a part goes down

| Part that goes down | What the user sees | What recovers by itself |
|---|---|---|
| Chat | The assistant shows "unavailable"; the rest works | `start` (or Docker) brings the chat back up |
| Calculation | Scores stop updating; the screens show the last calculation | The service comes back and processes the pending queue |
| API | The dashboard shows "API unavailable" in the sections and stops insisting for a few seconds (circuit breaker) | The API comes back and the screens refresh |
| Database | `/health` answers 503; the dashboard warns | Everything comes back when the database comes back |
| One section of the screen | Only that section shows the error with the code | The rest of the screen keeps going normally |

Each service writes a heartbeat to the database (`service_status`). Administration → Services and the diagnostics show how long ago each one sent a signal.

## 5. How to evolve the system

### 5.1 Changing a rule value (minimum grade, cutoffs, deadlines…)

**Do not touch the code.** Use Administration → Parameters. Every change is versioned, with author, date and justification. Minimum grade and risk cutoffs become a proposal and only apply after coordination approval. Recalculating all students is automatic.

### 5.2 Changing the database (new column, table, index)

```bash
python -m scripts.migrate --new "add guardian phone"
#  creates sql/migrations/002_add_guardian_phone.sql with a template header
#  write the SQL in the file
python -m scripts.migrate --list-items     # checks: 002 appears as pending
python -m scripts.migrate                  # applies it (all or nothing) and records it in schema_migrations
```

Rules:

- **An applied file is not edited.** To fix it, create another one. The script notices the edit through the hash and stops.
- A new table needs a `GRANT` for the user of the service that is going to use it (`mufasa_api`, `mufasa_chat` or `mufasa_calculation`).
- `build_database` applies all migrations at the end, so a database built from zero already comes out up to date.
- The tests also apply the migrations to the test database, so run `pytest` after creating one.

### 5.3 Changing the code

| To change… | Edit… | And test in… |
|---|---|---|
| A score formula | `app/calculation/score.py` (bump `CODE_VERSION`) | `tests/test_calculation.py` |
| An API route | `app/api/*_routes.py`; the SQL goes in `*queries.py`, always with `:name` parameters | `tests/test_api.py` or `test_flows.py` |
| Who can see what | `app/api/permissions.py` and `visibility.py` | `tests/test_api.py` |
| A screen | `dashboard/screens/<profile>.py`; colors and badges in `dashboard/ui.py` | `tests/test_dashboard.py` and in the browser |
| A chat answer | `app/chatbot/intents.py` and `service.py` | `tests/test_chatbot.py` |
| A configuration variable | `app/config.py`, `.env.example` and `scripts/configure.py` | `python -m scripts.diagnostics` |

Precautions the tests enforce:

- SQL built with variable text (f-string or concatenation) fails the `test_no_sql_built_with_variable_text` test. Always use parameters.
- Every new student route must go through the scope check, so one profile does not read a student of another.
- Every new dashboard section must stay inside `with ui.section():`, so an error in it does not bring the screen down.

### 5.4 Writing a new test

The database tests use small, known data (`tests/conftest.py`, `DATA` and `USERS`), so the expected result is exact. Template:

```python
import pytest
from tests.conftest import enter

pytestmark = pytest.mark.database

def test_teacher_does_not_see_student_of_another_class(client):
    header = enter(client, "prof.um")           # returns the header with the token
    r = client.get("/api/v1/students/ALU0003", headers=header)
    assert r.status_code == 403                 # same answer for "not allowed" and "does not exist"
```

Run only your test with `pytest -k teacher_does_not_see -v`.

### 5.5 Delivering a new version

1. `pytest`: everything must pass.
2. `python -m scripts.diagnostics`: it must show 0 failure.
3. Bump the version in `app/__init__.py` (`__version__`), following this rule:
   - 1.1.**1** for a fix;
   - 1.**2**.0 for a new feature;
   - **2**.0.0 for a change that requires building the database again or changes the API contract.
4. Write what changed in `CHANGELOG.md`.
5. On Docker, change the `mufasa:1.1.0` tag in `docker-compose.yml` and run `docker compose up -d --build`.

The version appears at `/health`, on the Administration → Services screen and in the diagnostics, so you can tell which version is running on each machine.

## 6. Frequent maintenance questions

- **A student says their level is wrong.**
  1. Coordination → student record → history: shows each calculation, with the factors and the parameter version.
  2. If the data is wrong, fix it through the data load (Administration → Loads); recalculation is automatic.
  3. The student can also dispute it from their screen.
- **The score does not update.** Run the diagnostics and look at "heartbeat of calculation" and "recalculation queue". If the queue only grows, see `logs/calculation.log`.
- **Recalculate everyone.** Administration → home → Recalculate, or `POST /api/v1/calculations`.
- **Change the password of a database user.** Change it in `.env` and run `python -m scripts.build_database`. Attention: this recreates the database; on a database with real data, use `ALTER ROLE ... PASSWORD` as postgres.
